# FBG Interrogator Control Software

Настольное приложение под Windows 10 для управления оптоволоконным интеррогатором
**FBG-Interrogator GC-97001C-03-01-A-F** (2000 Гц · 4 канала · прошивка 4.10 · SN 94401220).

Производитель прибора — Zhuhai Arcadia Optronix.

## Настройки и калибровки

Настройки лежат в `fbg_config.json` рядом с исполняемым файлом: ни базы, ни
реестра. Отсутствие файла ошибкой не является — приложение стартует на
умолчаниях и создаёт файл при первом сохранении. Файл, испорченный правкой
руками, приложение не роняет: битый JSON, чужая кодировка, неизвестное поле,
поле неверного типа и значение, отвергнутое проверкой, дают умолчание
и **названное** замечание, а не отказ старта. Опечатка при этом стоит одного
поля, а не всего раздела.

В файле стоит версия формата. Файл версии новее текущей не читается вовсе
и при сохранении откладывается в `*.bad`, а не затирается: частичное чтение
файла из будущего опаснее умолчаний, потому что незнакомые поля пропали бы
молча.

Из `DeviceProfile` в настройки попадает не всё, и разделение идёт по признаку
«кто владелец числа»:

| Владелец | Поля | В файле |
|---|---|---|
| прибор (`10 04`, `10 05`) | `channels`, `fbg_per_channel`, `sweep_speed_hz`, `peak_gap_ghz`, параметры развёртки | да, кэшем последнего опроса |
| скрининг | `sweep_base_ghz`, `freq_divisor`, `case_temp_scale`, `peak_missing_codes`, `adc_index_ascending_freq`, `mode_len_width`, `set_sweep_*` | нет |
| оператор | `case_temp_signed` (вопрос N2b открыт) | да |

Кэш геометрии нужен потому, что кольцо истории, буферы кадра и фильтр
телеметрии журнала строятся из профиля **до** подключения. Обновляет его
`profile_from_device` после успешного опроса конфигурации.

Поля второй строки настройкой не являются: их изменение означает, что прибор
**другой**, и правильный путь — новый скрининг и новые умолчания в
`profile.py`. Вписанное в файл руками такое поле игнорируется с явной причиной.
Довод — асимметрия цены ошибки: `sweep_base_ghz`, сдвинутый на единицу, даёт
систематические 8 пм, невидимые ни в одном числе на экране.

Калибровки — отдельный JSON. Датчик описывается **ожидаемой длиной волны
и окном поиска**, а не номером позиции в кадре (Р30): позиции — это слоты,
заполняемые по возрастанию λ по мере обнаружения, и на стенде 1551.5 нм лежит
в позиции 1, будучи четвёртой решёткой линии. Окно покрывает рабочий диапазон
датчика, а не паспортный разброс решётки: FBG даёт ≈10 пм/°C, и рабочие
−15…+55 °C требуют ±0.35 нм.

Исходов поиска три, и все различимы: один пик в окне — значение; ни одного —
`NaN`; **больше одного — тоже `NaN`**, а не ближайший из них. «Ближайший» —
монетка: если решётка датчика пропала, а в окне остался соседний пик, вернулась
бы чужая длина волны под именем этого датчика. Пересечение окон двух датчиков
одного канала ловится один раз при загрузке набора.

⚠️ Формула температурной компенсации — **гипотеза** (вопрос N22): из таблицы
`FBGInfo` штатного ПО известны только имена полей `TC_Coff` и `TC_Base`.

Идентификация прибора (`serial`, `firmware`) хранится в настройках один раз
и подставляется в шапки файла данных и журнала. Известна она только после
опроса конфигурации, поэтому в первом файле журнала первого запуска стоит
честное `unknown`: журнал создаётся раньше подключения, чтобы записать сам
обмен подключения.

## Приложение

```bash
python main.py
```

Три вкладки: **Подключение**, **Прибор**, **Журнал пакетов**.

Логика отделена от виджетов не ради стройности, а ради проверяемости: сборка
приложения (`fbg/ui/app.py`), модели панелей (`models.py`), тексты (`texts.py`)
и лестница диагностики (`diagnostics.py`) **не импортируют Qt** и проверяются
без экрана. Это закреплено дымовым тестом, который запускает импорт в отдельном
интерпретаторе — внутри общего прогона живут тесты, тянущие Qt намеренно.

Панели читают **снимок** (`AppController.snapshot()`) по таймеру 10 Гц и ничего
из ядра не держат. Событийного обновления нет: журнал видит каждую датаграмму,
и при 2000 Гц отрисовка по событию утопила бы UI.

### Первое, что делает приложение при подключении

Сверяет геометрию прибора (ответы `10 04` и `10 05`) с профилем из настроек.
`Session` профиль не обновляет намеренно — он нужен и без живого прибора, при
переразборе журнала, — поэтому `profile_from_device` зовёт приложение.

Совпало — идентификация прибора уезжает в настройки, и со следующего запуска
шапки файлов верны с первого байта. Разошлось — **не сохраняется ничего**, ни
профиль, ни серийный номер, а расхождение показывается построчно. Принять
геометрию прибора можно только явным действием, при закрытой связи и
остановленной записи: кольцо истории, буфер кадра и фильтр телеметрии журнала
уже выделены под старый профиль, поэтому смена геометрии пересобирает
компоненты.

### Диагностика подключения

Панель подключения показывает не «ошибка подключения», а лестницу из KB_01,
половину которой закрывают счётчики транспорта:

| Вердикт | Значение |
|---|---|
| `[ok]` | проверено кодом, претензий нет |
| `[!!]` | проверено кодом, вероятная причина отказа |
| `[ ? ]` | кодом не проверяется, делает человек |

`commands_sent > 0` при `datagrams_received == 0` — команды уходят, ответов
нет, то есть закрытый входящий UDP/8001 либо молчащий прибор.
`foreign_datagrams > 0` — отвечает кто-то другой. `icmp_resets > 0` — прибор
недоступен. Приём не на `0.0.0.0` — единственный пункт, проверяемый полностью:
это молчание при полностью исправной связи, и выглядит оно как «сеть
не работает».

### Порядок остановки

`Stop` прибору → сессия → recorder → журнал → pipeline. Сначала замолкает
источник, потом закрывается связь, потом писатели дописывают хвосты — им нужно
живое кольцо, — и последним гаснет тракт. Каждый шаг идёт в своём `try`: отказ
одного не оставляет прибор льющим поток.

### Подключение не блокирует окно

`Probing` — это `Stop` плюс пять чтений, каждое с таймаутом и повторами: на
молчащем приборе окно замерло бы на секунды. Поэтому `connect` уходит в обычный
`threading.Thread`, а результат забирает тот же таймер 10 Гц, которым UI и так
читает снимки. `QThread` поверх наших потоков не появляется: второго слоя
управления жизненным циклом здесь нет.

## Тесты

```bash
pytest                        # всё, кроме требующего прибора
pytest -m "not ui and not slow"   # ядро, как в CI
QT_QPA_PLATFORM=offscreen pytest -m ui   # интерфейс без экрана
pytest -m slow                # нагрузочные тесты 2 кГц на loopback
pytest -m device              # только при подключённом приборе
```

Тесты с маркером `ui` требуют PySide6; без него они пропускаются, а не падают,
поэтому job ядра в CI живёт в окружении вовсе без Qt.

Критерий нагрузочных тестов: симулятор шлёт 2000 кадров/с по 494 байта,
потери менее 0.1 % за 60 секунд.

* `tests/test_load.py` — сторона **отправки**: выдерживает ли симулятор темп.
* `tests/test_transport_load.py` — сторона **приёма**: доходят ли датаграммы
  до потребителя через `UdpTransport`, с разбором кодеком и без.
* `tests/test_pipeline_load.py` — **весь тракт**: симулятор → транспорт →
  сессия → pipeline → курсор писателя.
* `tests/test_recorder_load.py` — **тракт до файла**: то же плюс запись CSV
  на диск, с проверкой полноты по номерам кадров в самих файлах.
* `tests/test_packet_log_load.py` — **журнал в полном режиме**: симулятор →
  транспорт → `packet_log`, с замером объёма и проверкой того, что журнал
  не создаёт обратного давления на приём.

Измерено на loopback (Linux, 60 с × 2000 Гц): 119 945 отправлено, 119 945
дошло до потребителя, потери 0.0000 %, пик очереди 45 из 4096, межкадровый
интервал p50 499 мкс · p99 593 мкс · p99.9 795 мкс. Тот же прогон с полным
разбором каждого кадра — тоже без потерь.

Сквозной прогон через `pipeline` (Linux, 60 с × 2000 Гц): отправлено 120 001,
доехало до писателя 120 001, потери 0.0000 %, разрывов у писателя нет. Пик
очереди транспорта 39 из 4096, пик отставания писателя 59 кадров из 20 000,
кольцо 19.4 МБ. Задержка приёмного потока (от `recvfrom` до конца разбора)
p50 104 мкс · p99 241 мкс · p99.9 1108 мкс; задержка доставки писателю
p50 5.2 мс · p99 10.1 мс — в ней сидит его собственный опрос раз в 10 мс.
UI при этом обновлялся 19.9 раза в секунду, а не 2000: децимация по времени.

Запись на диск (Linux, 60 с × 2000 Гц, чат №7): отправлено 120 001, строк
в файлах 120 001, потерь и разрывов нет, 63.1 МБ в двух файлах (ротация
сработала на ходу), строка в среднем 551 Б при двух распознанных решётках.
Файл целиком ASCII, включая шапку: `numpy.genfromtxt` открывает его
в локальной кодировке ОС, и на Windows это cp1252. Порядок частей записи
восстанавливается алфавитной сортировкой имён и полем `file_part` в шапке,
но не временем создания файла: на Windows его разрешение грубее интервала
между ротациями.
Собственный потолок записи на худшем случае — все 120 позиций заполнены,
строка 1254 Б — 32 800 строк/с и 39 МБ/с, из них 83 % времени уходит
на форматирование. Запас над паспортными 2000 Гц — шестнадцатикратный,
поэтому децимация нужна ради объёма файлов, а не ради темпа.

Журнал пакетов (Linux, 60 с × 2000 Гц, чат №8): в полном режиме
120 004 записи, 177.3 МБ в трёх файлах, 2.95 МБ/с, запись в среднем 1549 Б.
Потери на приёме 0.0000 %, пик очереди транспорта 32 из 4096, журнал
не вытеснил ни одной записи — обратного давления на приём он не создаёт,
потому что `log_rx` только кладёт байты в свою очередь, а форматирование
и файл живут в отдельном потоке. Собственный потолок журнала — 134 000
записей/с и 198 МБ/с, поровну между форматированием и записью, запас
над паспортным темпом более чем полусотенный.

По умолчанию телеметрия в журнал **не пишется**: те же 15 секунд потока
дают файл в несколько сотен байт вместо 44 МБ. Полнота включается явно —
`telemetry_stride=1` — и по умолчанию ограничена 20 000 кадров, то есть
десятью секундами потока. Промежуточный режим `stride=N` стоит ровно
во столько раз меньше: при `stride=10` объём 0.30 МБ/с против 2.95 МБ/с,
отношение 10.0.

Файл журнала, как и файл измерений, целиком ASCII: его открывают Блокнотом
и импортируют в Excel, а кодировку по умолчанию там выбирает ОС. Поэтому
метки расшифровки английские (`Telemetry ch=4 filled=2`), а не переведённые.

## Как ведётся разработка

Проект развивается по одному модулю за раз. Каждый рабочий чат:

1. Клонирует репозиторий и фиксирует базовый коммит.
2. Пишет модуль вместе с тестами.
3. Отдаёт результат как патч в формате `git format-patch`.

Применение патча:

```bash
git pull
git am -3 chatNN_module.mbox
pytest
git push
```

Флаг `-3` обязателен: он включает трёхстороннее слияние и позволяет применить
патч, даже если ветка ушла вперёд.

Если патч не применился:

```bash
git am --abort
```

и вернуться в координационный чат с текстом ошибки.

## База знаний

Спецификация протокола, профиль прибора, архитектурные решения и журнал
открытых вопросов ведутся отдельно в файлах `KB_01`…`KB_06`.

**Приоритет источников:** реальные захваты трафика → файлы `KB_*` → PDF
производителя. В PDF производителя найдено не менее восьми фактических ошибок,
поэтому он используется как гипотеза, а не как факт.
